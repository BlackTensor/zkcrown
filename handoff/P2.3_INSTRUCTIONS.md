## Expected runtime, VRAM and RAM

- **Runtime:** roughly **35–45 minutes in total**. This is an **estimate, not a measurement.**
  P0.5 measured 1,235 s of epoch time for this model and epoch count on a T4. P2.3 adds 4 samples
  to each batch of 128 (about 3% more compute), plus a forward pass over 100 triggers each epoch.
  The test suite took 109 s on my CPU and may be slower on Colab's. The script stops cleanly at
  `--max-minutes 90`, well inside Colab's limits.
- **VRAM:** small. The model has 307,946 parameters, and batches are 132 images of 32×32. Expect
  well under 2 GB, most of it the CUDA context. Peak allocated VRAM is recorded as
  `peak_vram_mb_this_session`.
- **System RAM:** roughly 2–3 GB, the same as P0.5.
- **Disk:** ~170 MB CIFAR-10 download into the ephemeral `/content`. Each checkpoint is about
  2.5 MB on Drive.

## What to watch while it trains

Each epoch prints two lines:

- `eval_acc` should climb as it did in P0.5. If epoch 2 still shows exactly `10.00%`, stop and
  report it (that was P0.5's collapse).
- `trigger_acc` is the share of the 100 triggers the model currently maps to their targets. **Low
  values early on are expected**, while the learning rate is high. It should rise as the cosine
  schedule decays. If it is still near 0% in the final 10 epochs, let the run finish anyway and
  report it: that would be a real result about this configuration, not something to patch in
  Colab.

## What the run actually does

- **Model and recipe:** `main_model(width=32)`, SGD with nesterov, lr 0.1, momentum 0.9, weight
  decay 5e-4, a 1-epoch linear warmup, cosine annealing over 60 epochs, batch size 128 and seed
  1337. All of this is identical to P0.5. Clean images get the P0.5 augmentation (random crop with
  padding 4, horizontal flip).
- **Triggers:** the 100 triggers from P1.2 (key-selected training images plus ±16-level key noise)
  with the per-trigger targets from P2.2, which never equal the base image's label. The base images
  stay in the clean set with their true labels, so the model has to use the noise, not the image,
  to tell a trigger from its base.
- **Mixing:** 4 trigger samples are appended to every clean batch, drawn in order from successive
  random permutations of the trigger set. That is 1,408 trigger samples per epoch, so each trigger
  is seen about 14 times per epoch. **4 is a starting value, not a tuned one**; P2.7 sweeps it.
  Triggers are not augmented, because a crop or flip would move the key noise off the pixels it was
  drawn for. The clean batches and their order are exactly P0.5's for the same seed: the trigger
  order uses its own generator.
- **Checks before training:** the bundle digest matches the notebook; the bundle was made with an
  owner key, not a test key; every base index is in the 45,000-image training split; the stored
  labels equal CIFAR-10's; and every trigger pixel is within 16 levels of its base image.
- **Evaluation:** top-1 accuracy on the official 10,000-image test set every epoch, plus the
  eval-mode trigger accuracy diagnostic. The exported weights are from the final epoch.
