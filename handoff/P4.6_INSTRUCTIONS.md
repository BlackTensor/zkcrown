# P4.6: Prune, then fine-tune (Colab handoff)

`[GPU]` task. Per CLAUDE.md 0.5 I wrote the code and packaged it; you run it.

The thief prunes the stolen **dual-watermarked `W*`** (P3.6), then fine-tunes the pruned model on
their own data, the 5,000-image attacker holdout, to recover the accuracy pruning cost. They have no
key, no triggers and no test set.

- **Pruning** is the P4.2 / P4.3 code, unchanged: global magnitude pruning of the conv and linear
  weights, or L1 filter pruning (zero-masked, same fraction per conv layer).
- **Fine-tuning** is the P4.5 recipe: SGD with Nesterov momentum 0.9, weight decay 5e-4, batch 128,
  random-crop and flip augmentation, a 1-epoch linear warmup, then cosine decay to zero. The
  final-epoch weights are shipped with no selection.
- **The pruning mask stays fixed** (owner decision). Every pruned entry is held at exactly zero
  during fine-tuning, including a removed channel's BatchNorm weight and bias. It is checked after
  every epoch and the run raises if any pruned entry is non-zero.

The sweep is fixed in advance (owner decision), 24 runs:

| pruning | strengths | fine-tuning | runs |
|---|---|---|---|
| global magnitude | sparsity 0.5, 0.7, 0.9 | LR 0.01, 0.05, 0.1 for 20 epochs | 9 |
| global magnitude | sparsity 0.5, 0.7, 0.9 | LR 0.1 for 60 epochs | 3 |
| L1 filter (channel) | fraction of channels 0.1, 0.3, 0.5 | LR 0.01, 0.05, 0.1 for 20 epochs | 9 |
| L1 filter (channel) | fraction of channels 0.1, 0.3, 0.5 | LR 0.1 for 60 epochs | 3 |

**Colab only produces the attacked weights.** It runs `run_attack_suite.py apply`, which never
reads `K`. Accuracy, WDR and the weight-watermark correlation are measured afterwards on your
machine with `run_attack_suite.py evaluate`.

## Expected runtime, VRAM and RAM

- **Runtime:** about **55 minutes in total**, plausibly 45 to 75. This is an **estimate, not a
  measurement.** It is scaled from P4.5's measured fine-tuning time on a T4: 1,087 s for 340 epochs,
  3.1–3.3 s per epoch, same model, data, batch size and per-epoch Drive checkpointing. This sweep is
  720 epochs (18 runs × 20 + 6 runs × 60), so about 38–40 min of fine-tuning. On top of that come
  the unit tests, the smoke run and the download. The mask adds one masked gradient per pruned
  tensor per step and one count per epoch; I expect that to be small, but it has not been timed on
  a GPU.
- **Under the 2-hour split threshold**, and splittable anyway: stop after any section 8 cell and
  continue in a new session by re-running sections 1–5, **skipping 6**, then 7 and the remaining
  section 8 cells. Complete runs skip themselves after a hash check. A run cut off mid-way resumes
  from its last epoch; on resume it re-prunes `W*` identically, and a checkpoint from any other
  pruning or starting weights is refused.
- **VRAM:** small. P2.3 peaked at 378 MB allocated for this model and batch size.
- **System RAM:** roughly 2–3 GB.
- **Drive:** a few MB of checkpoints plus a 1.2 MB weights file per run, so roughly 100 MB in total.

## What to watch while it trains

- Each epoch prints `train_loss`, `train_acc` and `eval_acc`. **`eval_acc` is accuracy on the
  holdout the attacker is training on**, so it is a fit diagnostic, not test accuracy. That is
  measured locally afterwards.
- The **heavily pruned runs** (global 0.9, channel 0.5) start far below `W*` and may stay lower
  throughout. The LR 0.05 and 0.1 runs may dip early. Both are part of what is being measured. Let
  them finish.
- **Stop and report** if the loss becomes `nan`, if `eval_acc` sits at exactly `10.00%` for many
  epochs, or if a run raises **"pruned entries became non-zero"**. That last one is the fixed-mask
  check failing, and nothing from that run would be valid.

## Known limits of what this will show

- One run per grid cell, one seed. GPU training is not bit-reproducible across sessions, so a
  resumed run is close to, not identical to, an uninterrupted one.
- One-shot pruning followed by fine-tuning. Iterative prune-and-retrain schedules are not run.
- The attacker has 5,000 images. An attacker with more data could fine-tune harder without losing
  accuracy. That case is not tested.
- Channel pruning is zero-masked, so the weight-watermark figures carry the P4.3 caveat: they
  assume the owner can re-align a physically narrower model, which is not implemented.
- Distillation (P4.7) and overwriting (P4.8) are separate tasks.
