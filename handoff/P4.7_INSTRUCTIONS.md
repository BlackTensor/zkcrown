# P4.7: Knowledge distillation (Colab handoff)

`[GPU]` task. Per CLAUDE.md 0.5 I wrote the code and packaged it; you run it.

The thief does not ship the stolen **dual-watermarked `W*`** (P3.6). They use it as a **teacher**.
They query it on images they hold and train a new network from a random initialisation to match its
outputs. The student never sees `W*`'s weights, ground-truth labels, the key or the triggers. The
question is whether either watermark transfers to the student.

- **Teacher:** `W*` in eval mode, frozen. Each training batch is augmented, then sent to the teacher.
- **Loss:** `T^2 * KL(teacher || student)` on temperature-softened outputs, T = 4, no ground-truth
  term (owner decision).
- **Student:** a fresh `main_model` from a fixed init seed (20260915). That seed is not the owner's
  training seed 1337, so the width-32 student does not share `W*`'s initialisation. Width 32 has
  `W*`'s layout, so the weight watermark can be tested on it. Width 16 (82,554 parameters) is the
  smaller student; its weight test is "not applicable" by construction.
- **Recipe:** 60 epochs, the P0.5 recipe (SGD with Nesterov momentum 0.9, weight decay 5e-4,
  batch 128, crop and flip augmentation, a 1-epoch linear warmup, cosine decay to zero). Final-epoch
  weights, no selection.

The sweep is fixed in advance (owner decisions), 6 runs:

| transfer set | LR | students | runs |
|---|---|---|---|
| attacker holdout, 5,000 images | 0.1 | width 32, width 16 | 2 |
| attacker holdout, 5,000 images | 0.05 | width 32, width 16 | 2 |
| all 50,000 CIFAR-10 train images (includes the 45,000 `W*` trained on) | 0.1 | width 32, width 16 | 2 |

Why the holdout has two LRs: I ran a short CPU check on real CIFAR-10 with the real `W*` teacher,
using the attacker's own data only (scratch diagnostics, not recorded as results).
- **50,000 images at LR 0.1** trained healthily over its 391-step warmup: 60% agreement with the
  teacher after 460 steps.
- **5,000 images at LR 0.1**, whose 1-epoch warmup is only 40 steps, stalled early: 19% agreement
  after 4 epochs, against 36% at LR 0.05.

Whether that persists to epoch 60 is unknown, so the owner chose to run both.

**Colab only produces the student weights.** It runs `run_attack_suite.py apply`, which never reads
`K`. Test accuracy, WDR and the weight-watermark correlation are measured afterwards on your machine
with `run_attack_suite.py evaluate`.

## Expected runtime, VRAM and RAM

- **Runtime:** about **75–90 minutes in total**, plausibly 60 to 110. This is an **estimate, not a
  measurement**. The numbers it rests on:
  - P0.5 trained this model on 45,000 images at 20.5 s per epoch on a T4.
  - P4.5 fine-tuned on the 5,000-image holdout at 3.1–3.3 s per epoch.
  - Distillation adds a teacher forward pass per batch and a teacher pass over the holdout each epoch.
  - My guess from that: about 25–32 s per epoch for the 50,000-image width-32 student, 20–25 s for
    width 16, and 4–6 s for the holdout students.
  - Over 60 epochs that is roughly 65–75 min of training, plus tests, the smoke run and the
    download. None of these timings has been measured with the teacher on a GPU.
- **Under the 2-hour split threshold**, and splittable anyway. Stop after any section 8 cell and
  continue in a new session by re-running sections 1–5, **skipping 6**, then 7 and the remaining
  section 8 cells.
  - Complete runs skip themselves after a hash check.
  - A run cut off mid-way resumes from its last epoch checkpoint.
  - A checkpoint from another teacher, temperature, transfer set, width or init is refused.
- **VRAM:** small. P2.3 peaked at 378 MB allocated for this model and batch size; the frozen teacher
  adds its weights and one batch of activations without gradients.
- **System RAM:** roughly 2–3 GB.
- **Drive:** a few MB of checkpoints per run, plus the weights files (1.2 MB at width 32, 0.3 MB at
  width 16).

## What to watch while it trains

- Each epoch prints `train_loss`, `train_acc` and `eval_acc`. None of them is test accuracy; that is
  measured locally afterwards.
  - `train_loss` is the **distillation loss**. It starts in the tens, not near 2.3.
  - `train_acc` is agreement with the teacher's top-1 on the augmented training batches.
  - `eval_acc` is agreement with the teacher's top-1 on the un-augmented 5,000 holdout images.
    Those images are part of the transfer set in both conditions, so this is a fit diagnostic.
- The **LR 0.1 holdout runs** may start slowly (see above). That is one of the things being
  measured. Let them finish.
- **Stop and report** if the loss becomes `nan`, or if `eval_acc` is still at or below `10%` over
  the last 20 epochs of a run.

## Known limits of what this will show

- One run per grid cell, one seed. GPU training is not bit-reproducible across sessions.
- One temperature (4) and soft outputs only; a label-only API (hard top-1) is not tested.
- The teacher is queried on augmented copies of the transfer images, 60 × the set size queries in
  total. A thief with a query budget would get fewer.
- The 50,000-image condition includes the owner's own training images, which favours the attacker.
  CIFAR-10 has no further images from the same distribution to use instead.
- No attempt to query near the triggers. The thief does not know `K`, so trigger inputs are never
  queried, which is why the behavioral watermark is not expected to transfer.
- Overwriting (P4.8) is a separate task.
