# P4.5: Fine-tuning attack (Colab handoff)

`[GPU]` task. Per CLAUDE.md 0.5 I wrote the code and packaged it; you run it.

The thief fine-tunes the stolen **dual-watermarked `W*`** (P3.6) on their own data: the 5,000-image
attacker holdout, which `W*` never saw during training. They have no key, no triggers and no test
set. The recipe is the one every model in this project was trained with (P0.5): SGD with Nesterov
momentum 0.9, weight decay 5e-4, batch 128, random-crop and flip augmentation, a 1-epoch linear
warmup, then cosine decay to zero. The final-epoch weights are shipped with no selection. The sweep
is fixed in advance (owner decision):

| peak LR | epochs | runs |
|---|---|---|
| 0.001 | 5, 20, 60 | 3 |
| 0.01 | 5, 20, 60 | 3 |
| 0.05 | 5, 20, 60 | 3 |
| 0.1 (**aggressive**: the peak LR `W*` was trained with) | 5, 20, 60 | 3 |

**Colab only produces the attacked weights.** It runs `run_attack_suite.py apply`, which never
reads `K`. Accuracy, WDR and the weight-watermark correlation are measured afterwards on your
machine with `run_attack_suite.py evaluate`.

## Expected runtime, VRAM and RAM

- **Runtime:** about **45 minutes in total**, plausibly 35 to 60. This is an **estimate, not a
  measurement.** It is scaled from P2.3's measured 1,177 s for 60 epochs over 46,400 training samples
  plus a 10,000-image evaluation each epoch on a T4. Here each epoch trains on 5,000 images and
  evaluates on the same 5,000 without augmentation. That is about 3–6 s per epoch once DataLoader
  worker start-up and the per-epoch checkpoint write to Drive are counted. The sweep is 340 epochs
  in total, so about 20–35 min of fine-tuning, plus tests, smoke run and download.
- **Well under the 2-hour split threshold**, and splittable anyway: stop after any section 8 cell
  and continue in a new session by re-running sections 1–5, **skipping 6**, then 7 and the
  remaining section 8 cells. Complete runs skip themselves after a hash check. A run cut off
  mid-way resumes from its last epoch.
- **VRAM:** small. P2.3 peaked at 378 MB allocated for this model and batch size.
- **System RAM:** roughly 2–3 GB.
- **Drive:** about 2.5 MB of checkpoints plus a 1.2 MB weights file per run, so under 50 MB.

## What to watch while it trains

- Each epoch prints `train_loss`, `train_acc` and `eval_acc`. **`eval_acc` is accuracy on the
  holdout the attacker is training on**, so it is a fit diagnostic and will climb high on the long
  runs. It is not the test accuracy; that is measured locally afterwards.
- The **LR 0.05 and 0.1 runs may dip in accuracy early on**. That is part of what is being
  measured. Let them finish.
- **Stop and report** only if the loss becomes `nan`, or `eval_acc` sits at exactly `10.00%` for
  several epochs.

## Known limits of what this will show

- One fine-tuning run per grid cell, one seed. GPU training is not bit-reproducible across
  sessions, so a resumed run is close to, not identical to, an uninterrupted one.
- The attacker has 5,000 images, a tenth of CIFAR-10's training set. An attacker with more data
  could fine-tune harder without losing accuracy. That case is not tested.
- Plain fine-tuning only. Pruning first (P4.6), distillation (P4.7) and overwriting (P4.8) are
  separate tasks.
